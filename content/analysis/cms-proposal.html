Letting non-technical writers edit the Fireside Library

A simple proposal · June 2026

The goal: let a small team of trusted writers — think five people — add or improve firesides from a clean visual editor, with no Git, no terminal, and no Markdown frontmatter, while you keep version control and a review step before anything goes live. See “Scenario: five writers at once” for how the team workflow holds up.

The recommendation Pages CMS

Use Pages CMS (free, open-source, MIT). It gives writers a Google-Docs-style editor in the browser that reads and writes the Markdown files already sitting in content/firesides/. Your repo stays the single source of truth — the files survive even if the tool disappears — and the existing Astro build on Vercel is untouched.

Writer → app.pagescms.org (visual editor) → saves a commit on a branch → you review the change → merge → Vercel rebuilds → live

What changed since we last looked

The old objection to a Git-backed CMS was “every writer needs a GitHub account.” That’s no longer true. Pages CMS now supports email invites: you invite a writer by email, their edits are committed through a GitHub App on your behalf, and they never create a GitHub account or see GitHub at all. For a handful of trusted contributors, the onboarding friction is essentially gone.

The one real decision: how content is shaped

This is the part the generic write-up missed. Our firesides are not flat files with frontmatter. Today each fireside is a folder:

content/firesides/01-overview-of-the-bahai-faith/
   metadata.yaml  ← title, id, phase, topics, status
   drafts/V1.md   ← the actual writing (no frontmatter)
   research/

The build (web/src/lib/firesides.ts) is opinionated: it picks final.md over the highest v*.md over ai-draft-*.md, and strips %%…%% editorial notes so they never publish. A CMS expects one tidy file per entry, so we pick a lane:

OptionWhat it meansEffort
A. Fit the CMS to our model recommended Configure Pages CMS to edit metadata.yaml and the latest draft in place, keeping the current folder layout and build logic exactly as-is. Low — config only
B. Move to one-file-with-frontmatter Migrate each fireside to a single Markdown file with frontmatter (the CMS-native shape), and simplify firesides.ts to match. Medium — one-time migration + loader rewrite

Start with A. It’s the smallest change, leaves your AI-draft / versioning workflow intact, and we can always graduate to B later if the frontmatter shape proves cleaner for writers.

What the writer actually does

  1. Gets an email invite — one click, no account to create. (One-time.)
  2. Opens a clean list of firesides and clicks one, or hits “New.”
  3. Writes in a visual editor — headings, bold, links, block quotes — no Markdown syntax, no frontmatter.
  4. Sets status to in-review and saves. That’s it.

Keeping it safe

Two lightweight guardrails, no technical knowledge required from the writer:

1. A status field. Drafts carry draft → in-review → published. The site only renders published (and %%…%% notes are already stripped), so nothing half-finished can leak to the public page.

2. A review glance. Each save is a normal commit. You skim the change in GitHub and merge when it’s ready — the writer never knows a “pull request” existed. Later we can automate spell-check or a voice-rules pass on each change if useful.

Honest caveat. Pages CMS edits live content in your real repo. The status field plus the review-before-merge habit are what keep an accidental save from reaching readers — worth setting up on day one, not later.

Scenario: five writers at once

This is the real test. Here’s how a team of five works without stepping on each other — and why, given how this repo is laid out, that’s far less fragile than it sounds.

The setup (one-time, ~5 minutes)

You send five email invites from Pages CMS. Each writer gets a magic-link login — no GitHub account, no install. All five point at one shared content branch (call it content), not at main. The public site keeps building from main, so nothing the five do is live until you merge.

5 writers → each save = 1 auto-commit to branch content → you review content vs main → merge → Vercel rebuilds main → live

Why they don’t collide: one fireside = one folder

Each fireside is its own folder (NN-slug/) with its own metadata.yaml and drafts/ files. Two writers working on different firesides are editing different files — so Git merges their commits cleanly and a conflict is structurally impossible. A conflict can only happen if two people edit the same fireside at the same moment. So the only coordination rule the team needs is plain editorial assignment:

The one rule: one writer “owns” a fireside at a time. The status field in metadata.yaml is the signal — if it’s drafting with someone’s name on it, others leave it alone. No locking software needed; it’s a whiteboard rule, enforced by the status field everyone can see.

How versioning works — two layers

Don’t confuse the CMS with the version history. There are two independent layers, and that’s a feature:

LayerWhat it gives you
Git history (automatic) Every save is a commit, so every revision of every fireside is recoverable, diffable, and attributable to a writer — forever. This is the real safety net. Nobody can lose work or silently overwrite someone; a bad edit is one revert away.
Draft files (editorial) The repo’s own convention, unchanged: AI starts in ai-draft.md; a writer’s revisions are v1.md, v2.md…; and on approval an editor promotes the chosen draft to final.md. The build prefers final.md > highest v*.md > ai-draft, so promotion is publishing.

For a CMS team, the smooth path is: writers edit their current v*.md in place and let Git history be the “versions” — spinning up a brand-new v3.md by hand is a power-user move that doesn’t fit a visual editor. Creating a fresh numbered draft stays available for a deliberate “start-over” rewrite; it’s just not the default.

The review loop (who plays editor)

With five writers you want one or two people in the editor seat. Their job isn’t technical:

  1. Writers move a fireside’s status to review when it’s ready for eyes.
  2. The editor skims the change on the content branch (a normal GitHub diff — or a one-screen review tool), leaves notes if needed.
  3. When it’s good, the editor promotes it to final.md / status: beta and merges content → main.
  4. Vercel rebuilds. The writers never saw a “pull request” or touched main.

Cadence is up to you — merge continuously, or batch a weekly “publish”. Because writers work off content, an in-progress draft never blocks a finished one from shipping.

Tracking who changed what — and talking to the editor

Two things you’ll want with five people: accountability (who edited what) and a back-channel (writer ↔ editor notes). Both exist — one needs a config flag.

Per-editor attribution. Each save is a commit, so Git history already records every change. But by default Pages CMS stamps commits with the app’s identity — meaning all five writers would look the same in history. One setting fixes it: commit.identity: user stamps each commit with that writer’s own name and email, so git blame, the GitHub history, and the in-app change log all show exactly who touched which fireside. Commit messages are templatable too, so they read in plain English:

settings:
  commit:
    identity: user  ← attribute each save to the real writer
    templates:
      update: "{userName} edited {path}"
      create: "{userName} added {path}"

Result in history: Sara Khan edited content/firesides/08-prayer/drafts/v2.md — not an anonymous app commit.

Comments for the editor. Three channels, use whichever fits:

ChannelGood for
Inline comments in Pages CMSWriter ↔ editor notes attached to a specific spot in the content, without leaving the editor. The native, no-Git option.
GitHub review commentsThe editor commenting on the change/diff during review — threaded, resolvable, tied to the exact line that changed.
%%…%% in-body notesAlready works today: a writer can leave a note right in the draft (“not sure about this quote”). The build strips %%…%%, so it never reaches readers.

Honest limits at five people

  • Same-file collisions still need the “one owner” rule. If two people do edit one fireside at once, the second save can hit a Git conflict, and Pages CMS has no rich in-app conflict resolver — you’d untangle it in GitHub. Distinct-folder work avoids this entirely; the rule is the cheap insurance.
  • Someone has to own the merge. Five writers means at least one editor who reviews and merges. It’s a light, non-technical role, but it has to exist — otherwise content just accumulates and nothing ships.
  • All five share one branch. Simplest by far for a trusted team. If you later want each writer fully sandboxed (strict per-person sign-off, or co-editing the same file), that’s branch-per-writer — more isolation, but more setup, and only worth it past this scale.

The escape hatch: it’s ours if we need it

Pages CMS is MIT-licensed and open-source, so we’re never locked in. Three levels of control, in order:

LevelWhen you’d use it
Hosted (app.pagescms.org)Default. Zero setup, just invite writers. Start here.
Self-host the stock appIf you want the editor on our own Vercel project / domain — one-click deploy, still the standard tool.
Fork & customizeIf we ever need a tailored editor — e.g. enforce the quote/voice rules in the UI, or match our content model exactly. We own the code and change whatever we want.

The point: we can adopt the hosted version today for near-zero effort, knowing that forking is always available as a fallback — and because the content is just Markdown in our repo, switching levels (or leaving entirely) costs nothing.
